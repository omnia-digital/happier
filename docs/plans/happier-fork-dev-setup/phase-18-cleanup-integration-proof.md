## Finding and evidence basis

**Derived: exact current-commit ancestry in a freshly observed permitted remote target is sufficient integration proof.** It does not require an immutable PR source snapshot. Let `C` be the current claimed local branch OID and `T` the live target OID in the exact expected provider host/repository. An unmodified Git object graph with `git --no-replace-objects merge-base --is-ancestor C T` returning 0 proves that `C` and its history are reachable from `T`. Git documents exit 1 as false and other nonzero exits as errors ([Git merge-base](https://git-scm.com/docs/git-merge-base)). This proves historical integration, not that later target changes have retained every original line; a revert does not erase history.

This corrects the overly broad phase13 statement that target ancestry cannot establish later local work was integrated: ancestry of an **old** source or a stale target cannot; ancestry of the **exact current** source against the **live** target can. Phase16's current checks still intentionally provide publication only. No phase13/16 contract or source is amended by this report.

**Observed vendor contract:** normal GitHub merges preserve source commits; squash creates a replacement commit; GitHub rebase creates new OIDs and drops originally empty commits ([GitHub merge strategies](https://docs.github.com/en/pull-requests/reference/pull-request-merges)). Accordingly, the useful first increment is ancestry proof, normally covering regular merge/fast-forward histories. It can also accept a source OID independently reachable after another integration; it must not classify by a guessed PR merge method. Squash/rebase whose original `C` is absent from the target remain unsupported.

**Observed provider limitation:** the [commit-associated PR endpoint](https://docs.github.com/en/rest/commits/commits#list-pull-requests-associated-with-a-commit) distinguishes commits already present in the default branch from commits absent there. For the latter it returns associated open and merged PRs. That weaker association is the relevant case for original squash/rebase OIDs. Exact `head.sha == C`, matching head/base repository, merged state and reachable merge result narrow the candidate but the documented association does not establish that `C` was included in the merge-time source snapshot, excluding all later commits. The [PR REST contract](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request) does specify the merged result OID: merge commit, squash result, or updated base tip for rebase. Reachability of that OID proves the result is in the target; it does not supply the missing source-to-result binding. A PR commit list is not a documented immutable merge snapshot either and the REST list is capped at 250 commits.

The [GraphQL PullRequest contract](https://docs.github.com/en/graphql/reference/pulls#pullrequest) preserves an associated head OID even when its ref is deleted; it does not describe that value as frozen at merge. Its `MergedEvent` exposes a merge-associated commit/ref, not an explicit source-head-at-merge field. No claim is made that GitHub actually mutates merged head fields; the missing guarantee is the finding. A public example or a synthetic provider fixture cannot establish that guarantee. The current API docs display REST version `2026-03-10`; research read on 2026-10-23, with no authenticated/private provider reads or writes.

## Conservative proof decision table

All rows concern integration evidence only. Phase16's custody, fresh archived owner-session, exact provider-qualified merged/non-draft PR and live source-ref publication requirements remain prerequisites; every actual resource decision still skips.

| Observed case | Integration conclusion and conservative disposition |
| --- | --- |
| Exact `C` is ancestor of live permitted `T`, all identities match | Integration proven for those OIDs. No immutable PR head-at-merge assertion needed. |
| Normal merge, but target OID/history missing locally | Unknown; preserve. A stale tracking ref is insufficient. |
| Squash/rebase result is reachable, original `C` is not; associated PR matches current head | Unknown source-to-result binding; preserve even if trees/patches match. |
| Later local ordinary or empty commit | Re-evaluate **new** `C`; prior proof never carries over. If absent from `T`, preserve. Empty/tree-identical commits still count. |
| Live source ref advances or is force-pushed away from `C` | Existing publication prerequisite fails; preserve even if old `C` remains integrated. |
| Live source ref is deleted | Ancestry may independently prove publication in the target, but phase16 requires a matching live source ref; preserve until root explicitly approves that policy change. |
| Target advances normally | Re-read its OID and evaluate the current pair; no cached positive result. |
| Target is rewritten/deleted, becomes unpermitted, or changes during observation | Invalidate the observation; preserve/retry. Never use the old fetched/tracking OID as current truth. |
| Wrong fork/repository/provider host, ambiguous remote, mismatched fetch/push identity | Preserve. Identical OIDs or owner/repository text without the correct host are insufficient. |
| Fresh PR is open/reopened, closed-unmerged, draft/unknown, or source/base/link identity changes | Existing PR prerequisite fails; preserve. Do not infer legal state transitions from fixtures; test unexpected responses as contradictory data. |
| Multiple linked/associated PRs | No first-result shortcut. A candidate must independently satisfy every required identity/policy/proof condition; conflicting relevant identity or incomplete required evidence is unknown. Do not let an unrelated merged PR supply another candidate's facts. |
| Provider or remote unavailable; malformed/partial/paginated response incomplete | Preserve. An ancestry fact does not bypass the existing fresh-PR prerequisite. |

The parent-approved target set must be explicit at the Git owner: current remote default and existing `dev`/`develop` are the local reference script's policy, not a Git/provider guarantee or an already implemented Happier policy. A PR's arbitrary base branch cannot nominate itself as a cleanup-safe integration target. A useful first implementation may use only the live default branch, but that scope choice belongs to root review.
