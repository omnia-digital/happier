# OH-60: Independent status sorting and grouping

## Context and scope

Continue the authorized Happier project on the existing feature branch. OH-60 adds Agent Status and Ticket Status to independent sidebar grouping and sorting choices. OH-57 owns runtime meaning, OH-58 owns provider ticket status, and OH-14 owns organization. Reuse those owners; do not add another classifier, reader, persisted status cache or organization store. Preserve the running daily app. Native acceptance remains a separate gate.

## Design constraints

- Extend existing grouping controls. A status group replaces machine/repository presentation while retaining saved organization for restoration. Preserve the applicable Pinned section and folder intent; document their exact interaction after inspecting current projection owners.
- Keep sorting independent: Ticket Status groups can sort by Agent Status. Reuse existing preference storage/default conventions; current ordering is an account preference, so do not invent a competing local setting.
- Reuse OH-57 canonical states and labels. Prefer attention first: error and needs input before working, queued/transient states, idle and finished. Name every supported state in the final deterministic ordering and preserve stable ties.
- Preserve custom ticket workflow names and provider-supplied order within the same provider/workspace/workflow. Across workflows use deterministic provider/workspace/workflow ordering; unrelated numeric ranks are not one global workflow.
- Keep No ticket distinct from linked-unavailable. Loading, stale and revoked states remain honest and agree with row badges.
- Reuse OH-58 shared scoped status projection. List demand cannot depend on a row already being visible in a status group. Define bounded demand and account invalidation through that owner before coding; no second request owner.
- Preserve selection, visible-index keyboard navigation, filters, manual ranks and machine/repository identity. Updates can move rows without duplicating sessions or rewriting manual organization.

The existing consumer is `useSessionListViewState`, after OH-14's machine/folder/repository presentation and before selected-row mapping and the visible keyboard index. `sessionListOrderingModeV1` is account scoped; `sessionListMachineViewV1` is local. Account parsing preserves unknown fields but resets unknown values of known enum fields. Therefore add an account-scoped status-sort override (`none`, `agent`, `ticket`) alongside the existing sort choice, and a local status-group choice with the same values. Selecting a standard sort clears the override. Selecting a standard presentation clears status grouping. Existing manual/created/updated and machine/repository choices remain intact and resume when the override is cleared. Older clients retain the additive account key while using their supported base sort; no relay change is required.

Status grouping replaces project/date/machine/repository headers, inside the existing server/activity/attention/working/shared/Pinned bands. Physical folder headers and nesting remain outer containers; status groups apply to each folder's direct members, while unfiled members combine within their band. Empty folders remain visible. Grouping never changes assignment, rank, repository association or target-machine identity. Sort-only modes preserve the full existing header/folder tree and sort sibling session rows only. Status-generated order disables structural drag ranking; explicit folder assignments and pin actions retain their existing owners. Controls explain this relationship. Status groups are generated after search/tag/folder focus filtering, before selection mapping; their rows rebuild the same canonical keyboard index. Clearing either override restores the underlying saved presentation/order without writes to organization.

Agent order is exhaustive over OH-57's `SessionListVisualStatus`: error, input, delivery_blocked, working, resuming, queued, archiving, offline, idle, finished, cancelled. Derive it with the same `getSessionStatus` → `deriveSessionListVisualStatus` path and use the existing badge labels. Ties retain source/manual order, then scoped session identity if needed; a status change moves a row without changing session identity or route selection. Runtime freshness uses the existing shared session-list clock and expiry wakes, not a new polling policy.

Ticket comparison separates provider/workspace/workflow scopes lexicographically (provider, workspace ID, workflow ID); only within a known shared workflow does an actual provider numeric workflow order take precedence, followed by status name and ID. Missing workflow identity uses status name/ID and never compares numeric ranks; within a known workflow, supplied ranks precede statuses without a supplied rank. Custom names remain verbatim. Last successful statuses are presented in explicitly qualified Checking/Stale groups; they are not live authority. Linked rows with no successful status use Checking ticket or Ticket unavailable, separate from No ticket. These labels agree with OH-58's visible status labels. Scoped status identity and freshness qualifiers are part of group identity, preventing same-named unrelated workflows from merging.
